# Metrics Agent Documentation

> **This file is documentation, not a prompt.** Unlike `agents/gtm/skill.md`,
> `agents/finance/skill.md` and `agents/creative/skill.md`, nothing loads this file into an
> LLM — the Metrics Agent is fully deterministic and makes no model calls. It is named
> `skill.md` only for symmetry with the other agent folders. Editing it changes no
> behaviour; the logic lives in `agents/metrics/agent.py`. Consider renaming it to
> `README.md` to stop it reading as a live prompt.

## 1. Purpose

The **Metrics Agent** is a LangGraph subgraph used in the Autonomous Marketing System to define campaign success metrics, set KPI targets, validate those targets against channel benchmarks, and align the output with the GTM Agent's recommended channel strategy.

The Metrics Agent operates after the GTM Agent has created a strategy plan. The GTM Agent selects channels and assigns weights, while the Metrics Agent decides what success means for those channels and whether the plan is realistic.

---

## 2. Role in the Autonomous Marketing System

The Metrics Agent is part of the strategy phase.

```text
Campaign Brief
   ↓
GTM Agent
   ↓
Channels + weights + positioning + pricing
   ↓
Metrics Agent
   ↓
Primary KPI + secondary KPIs + channel targets + alignment status
```

The Metrics Agent does **not** create ad copy, allocate budget, or publish campaigns. Its responsibility is KPI and target reasoning.

---

## 3. Inputs

The Metrics Agent expects campaign context from the shared campaign state.

Typical inputs include:

```python
{
    "product": "Flight Sale",
    "objective": "bookings",
    "total_budget": 100000,
    "channels": [
        {"name": "Google Search", "weight": 50, "priority": "high"},
        {"name": "Meta", "weight": 25, "priority": "medium"},
        {"name": "Email", "weight": 25, "priority": "medium"}
    ],
    "memory": InMemoryStore(),
    "negotiation_round": 0,
    "feedback": []
}
```

### Key input fields

| Field | Meaning |
|---|---|
| `product` | Campaign product, such as Flight Sale or Gift Card Sale |
| `objective` | Campaign goal, such as bookings, revenue, sales, signups, leads, trials, awareness, or reach |
| `total_budget` | Total available campaign budget |
| `channels` | GTM-selected channels with weights and priority |
| `memory` | Historical campaign memory store |
| `negotiation_round` | Number of target negotiation attempts already completed |
| `feedback` | Strategy-level feedback sent back to GTM when channel plan needs revision |

---

## 4. Outputs

The Metrics Agent writes KPI and alignment fields back into the shared campaign state.

Main outputs:

```python
{
    "primary_kpi": "ROAS",
    "secondary_kpis": ["CPA", "CTR", "Conversion Rate"],
    "manual_targets": {...},
    "historical_performance": [...],
    "learned_targets": {...},
    "global_targets": {...},
    "benchmark_data": {...},
    "channel_targets": {...},
    "metrics_issues": [...],
    "alignment_status": "aligned",
    "feedback": []
}
```

### Final status values

| Status | Meaning |
|---|---|
| `aligned` | Metrics targets and GTM strategy are compatible |
| `warnings` | Strategy can proceed, but Metrics Agent found some concerns |
| `halt` | Strategy has serious unresolved target issues |

## 5. KPI Logic

The Metrics Agent first maps the campaign objective to primary and secondary KPIs.

### Objective-to-KPI examples

| Objective | Primary KPI | Secondary KPIs |
|---|---|---|
| `bookings` | ROAS | CPA, CTR, Conversion Rate, Revenue, Conversions |
| `revenue` | ROAS | CPA, CTR, Conversion Rate, Revenue |
| `sales` | ROAS | CPA, CTR, Conversion Rate, Revenue |
| `signups` | CPA | Conversions, CTR, CPC, Conversion Rate |
| `leads` | CPA | Conversions, CTR, CPC, Conversion Rate |
| `trials` | CPA | Trial Starts, CTR, CPC, Conversion Rate |
| `awareness` | CPM | Impressions, Reach, CTR, Frequency |
| `reach` | Reach | Impressions, CPM, Frequency, CTR |

The objective-level KPI mapping is defined in `OBJECTIVE_KPI_CONFIG`.

## 6. Benchmark Logic

The Metrics Agent uses a static benchmark database as a cold-start prior.

Benchmarks are stored per canonical channel name.

Example:

```python
BENCHMARK_DB = {
    "Google Search": {
        "cpa_range": [250, 900],
        "roas_range": [2.5, 6.0],
        "ctr_range": [2.0, 7.0],
        "conversion_rate_range": [1.5, 6.0],
        "cpm_range": [80, 300]
    }
}
```

### Target vs benchmark

| Concept | Meaning |
|---|---|
| Target | What the campaign wants to achieve |
| Benchmark | What is considered realistic for the channel |

Example:

```text
Target ROAS = 7.0
Meta benchmark ROAS range = 2.0 to 5.0
```

The Metrics Agent should flag this as too aggressive.

## 7. Historical Learning

The Metrics Agent can use historical campaign memory.

Historical data is loaded from:

```python
state["memory"].get_relevant_history(...)
```

The memory store may currently be an in-memory store, but later it can be replaced with PostgreSQL.

Historical performance is used to improve targets.

Example:

```text
Previous Email ROAS = 9.0
Learned Email ROAS target = 9.0 × 1.10 = 9.9
```

The Metrics Agent marks targets as:

| Confidence | Meaning |
|---|---|
| `prior` | Cold-start target based on benchmark/manual config |
| `learned` | Target is based on historical campaign performance |

---

## 8. Check-Before-Clamp Logic

A key design point is **check-before-clamp**.

The Metrics Agent stores both:

```text
raw target = target before benchmark correction
final target = target after benchmark clamp
```

This matters because if the system only checks already-clamped values, unrealistic target issues may never be detected.

Example:

```text
Raw Email ROAS target = 27.5
Email benchmark max ROAS = 20.0
Final Email ROAS target = 20.0
```

The raw value allows the GTM Alignment step to detect that the original target was too aggressive.

---

## 9. GTM Alignment Logic

The `gtm_alignment` node checks two categories of issues.

### 9.1 Target-level issues

Target-level issues are handled inside the Metrics Agent through negotiation.

Examples:

```text
ROAS target too aggressive
CPA target too aggressive
CTR target too aggressive
CPM target too aggressive
Conversion Rate target too aggressive
```

These issues are resolved by accepting benchmark-clamped target values.

---

### 9.2 Strategy-level issues

Strategy-level issues are sent back to the parent campaign graph as feedback for the GTM Agent.

Example:

```text
Email has strong benchmark potential but GTM assigned it low/medium weight.
```

The Metrics Agent may send feedback such as:

```text
Increase Email weight because Email has stronger expected ROAS than current priority suggests.
```

This enables the cross-agent loop:

```text
GTM Agent → Metrics Agent → Feedback → GTM Agent revision
```

---

## 10. Negotiation Loop

The Metrics Agent has an internal negotiation loop for target-level issues.

```text
channel_target
   ↓
gtm_alignment
   ↓
if target issue exists and rounds < 3:
       negotiation
       ↓
       gtm_alignment again
else:
       final_decision
```

The maximum negotiation attempts are controlled by:

```python
MAX_NEGOTIATION_ROUNDS = 3
```

Negotiation does not change the GTM channel plan. It only adjusts KPI targets to realistic values.

---

## 11. Performance Feedback Loop

After campaigns go live, the Metrics Agent can score live performance against planned targets.

The `performance_feedback` node compares live results against targets:

```text
ROAS higher than target → positive score
CPA lower than target → positive score
CTR higher than target → positive score
Conversion Rate higher than target → positive score
```

It classifies each channel as:

| Status | Meaning |
|---|---|
| `winner` | Channel is beating targets |
| `loser` | Channel is missing targets badly |
| `learning` | Channel needs more data or is mixed |

The feedback loop writes results back into memory, so future campaigns can learn from them.

## 12. LangGraph Nodes

The Metrics Agent is built as a LangGraph subgraph.

### Planning subgraph nodes

```text
START
  ↓
kpi_selector
  ↓
manual_target_setter
  ↓
historical_data_loader
  ↓
learning_target
  ↓
benchmark_checker
  ↓
channel_target
  ↓
gtm_alignment
  ↓
negotiation OR final_decision
  ↓
END
```

### Node responsibilities

| Node | Responsibility |
|---|---|
| `kpi_selector` | Select primary and secondary KPIs based on objective |
| `manual_target_setter` | Create initial targets from manual rules |
| `historical_data_loader` | Fetch past campaign data from memory |
| `learning_target` | Create learned global targets from history |
| `benchmark_checker` | Load channel benchmark ranges |
| `channel_target` | Create per-channel raw and final targets |
| `gtm_alignment` | Detect target-level and strategy-level issues |
| `negotiation` | Resolve target-level issues by accepting clamped targets |
| `final_decision` | Set alignment status and feedback |

## 14. Relationship with GTM Agent

The GTM Agent creates the strategy pack and chooses channels with weights.

The Metrics Agent consumes those channels and validates them against KPI logic.

```text
GTM Agent owns:
- Product archetype
- Positioning
- Channel selection
- Channel weights
- Promo pricing

Metrics Agent owns:
- Primary KPI
- Secondary KPIs
- Channel targets
- Benchmark checks
- Historical learning
- Alignment status
- Feedback to GTM
```

The GTM Agent documentation states that the GTM Agent feeds into the Metrics Agent, Finance Agent, and Creative Agent. The Metrics Agent therefore depends on the GTM Agent's channel selection and strategy pack.

## 15. Current MVP vs Future Improvements

### Current MVP

```text
- Static benchmark database
- In-memory or injected memory store
- Deterministic target setting
- Internal target negotiation
- Strategy feedback to GTM
- Performance feedback scoring
```

### Future improvements

```text
- Replace in-memory store with PostgreSQL
- Add richer channel-level historical data
- Add confidence thresholds based on sample size
- Add guardrails for maximum target movement per cycle
- Add LangSmith tracing
- Add dashboard visualization for graph state updates
```

---

## 16. Important Notes

- Benchmarks are not final targets; benchmarks are guardrails.
- Manual targets are fallback defaults.
- Historical data improves targets when available.
- Raw targets are preserved so unrealistic assumptions can be detected.
- Target-level issues are handled inside Metrics Agent.
- Strategy-level issues are sent back to GTM Agent through parent graph feedback.
- The performance feedback graph closes the learning loop by saving live results into memory.
